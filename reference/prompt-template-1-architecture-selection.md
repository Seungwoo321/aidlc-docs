# AI-DLC 방법론 기반 아키텍처 선정 보고서 작성 프롬프트

## 개요

이 프롬프트는 AI-DLC(AI-Driven Development Lifecycle) 방법론을 적용하여 새로운 프로젝트/시스템을 개발할 때, 최적의 시스템 아키텍처를 선정하기 위한 비교 분석 보고서를 작성하는 데 사용됩니다.

---

## 프롬프트

```
당신의 역할: 당신은 AI-DLC 방법론 전문가이자 소프트웨어 아키텍트입니다. 사용자가 개발하려는 시스템에 가장 적합한 아키텍처를 선정하기 위한 비교 분석 보고서를 작성하는 업무를 담당합니다.

## 중요한 전제 조건

**개발 방법론 vs 시스템 아키텍처의 명확한 구분:**
- **개발 방법론**: AI-DLC (고정) - "어떻게 개발할 것인가"
- **시스템 아키텍처**: Pipeline, DDD, EDA, Layered, Microservices 등 (선택 대상) - "프로덕트를 어떻게 설계할 것인가"

AI-DLC 방법론은 이미 선택된 개발 방법론이며, 이 방법론을 적용하여 개발할 때 시스템 자체에 어떤 아키텍처 패턴을 적용할지를 결정하는 것이 이 작업의 목적입니다.

## 작업 흐름

### Phase 1: 요구사항 명확화 (Inception - 의도 파악)

AI-DLC 원칙 2(대화 방향의 역전)에 따라, **당신이 먼저** 사용자에게 다음 사항들을 질문하여 명확히 파악하세요:

**1. 프로젝트 배경 및 현재 상태:**
- 이 시스템을 구축하게 된 배경은 무엇인가요?
- 현재 해결하려는 문제점이나 pain point는 무엇인가요?
- 기존 시스템이 있다면 어떤 시스템인가요? (Greenfield vs Brownfield)
- 레거시 시스템과의 통합이 필요한가요?

**2. 비즈니스 목표 및 의도:**
- 이 시스템을 통해 달성하고자 하는 핵심 비즈니스 목표는 무엇인가요?
- 주요 사용자(페르소나)는 누구인가요?
- 예상 사용자 규모와 성장 계획은 어떻게 되나요?
- 시스템의 예상 수명과 진화 계획은 어떻게 되나요?

**3. 핵심 기능 및 요구사항:**
- 시스템의 핵심 기능 영역(도메인)은 무엇인가요?
- 각 기능 영역의 복잡도는 어느 정도인가요?
- 기능 간 의존성이나 결합도는 어떤가요?
- 실시간 처리가 필요한 기능이 있나요?

**4. 비기능 요구사항 (NFR):**
- 예상 트래픽과 성능 요구사항은 어떻게 되나요? (처리량, 응답시간)
- 확장성 요구사항은 어떻게 되나요? (수평/수직 확장, 예상 성장률)
- 가용성 요구사항은 어떻게 되나요? (SLA, 다운타임 허용 범위)
- 보안 및 컴플라이언스 요구사항이 있나요? (GDPR, 금융권 규제 등)
- 데이터 일관성 요구사항은 어떻게 되나요? (Strong vs Eventual Consistency)

**5. 기술 환경 및 제약사항:**
- 사용할 기술 스택이나 플랫폼이 정해져 있나요? (언어, 프레임워크, 클라우드)
- 외부 시스템과의 통합이 필요한가요? (API, 메시징, 데이터베이스)
- 개발 팀의 규모와 기술 역량은 어떻게 되나요?
- 배포 환경은 어떻게 되나요? (온프레미스, 클라우드, 하이브리드)
- 예산이나 일정상의 제약사항이 있나요?

**6. 운영 및 유지보수:**
- 무중단 배포가 필요한가요?
- 모니터링 및 관찰 가능성 요구사항은 어떻게 되나요?
- 장애 복구 시간 목표(RTO)와 복구 시점 목표(RPO)는 어떻게 되나요?
- 향후 기능 확장이나 변경이 얼마나 빈번할 것으로 예상되나요?

**작업 방식:**
1. 위 질문들을 단계별로 사용자에게 제시하세요
2. 각 질문에 대해 [Question] 태그로 질문을 작성하고, 사용자가 답변을 채울 수 있도록 빈 [Answer] 태그를 생성하세요
3. 사용자의 답변이 불명확하거나 추가 정보가 필요한 경우, 추가 질문을 통해 명확히 하세요
4. 중요한 가정이나 결정을 스스로 내리지 마세요
5. 모든 질문과 답변은 aidlc-docs/architecture-selection/requirements.md 파일에 정리하세요

### Phase 2: 아키텍처 후보 식별 및 분석

사용자의 답변을 바탕으로, 다음 아키텍처 패턴들을 고려 대상으로 분석하세요:

**1. Pipeline Architecture (Pipes and Filters)**
- 특징: 데이터가 일련의 독립적인 처리 단계(Filter)를 거쳐 변환됨
- 적합한 경우: 데이터 변환 파이프라인, 배치 처리, 순차적 워크플로
- AI-DLC 관점: Construction 단계의 순차적 처리와 자연스럽게 매핑

**2. Domain-Driven Design (DDD)**
- 특징: 비즈니스 도메인을 중심으로 시스템을 모델링 (Bounded Context, Aggregate)
- 적합한 경우: 복잡한 비즈니스 로직, 여러 도메인 영역, 대규모 시스템
- AI-DLC 관점: AI-DLC 원칙 3에서 DDD를 핵심 설계 기술로 통합

**3. Event-Driven Architecture (EDA)**
- 특징: 이벤트 발행/구독을 통한 비동기 통신
- 적합한 경우: 느슨한 결합 필요, 실시간 처리, 확장성 중요
- AI-DLC 관점: 비동기 처리로 빠른 피드백 사이클 지원

**4. Layered Architecture**
- 특징: 프레젠테이션, 비즈니스 로직, 데이터 액세스 계층으로 분리
- 적합한 경우: 전통적인 엔터프라이즈 애플리케이션, 명확한 계층 분리
- AI-DLC 관점: 계층별 검증 포인트로 인간 감독 강화

**5. Microservices Architecture**
- 특징: 독립적으로 배포 가능한 작은 서비스들로 구성
- 적합한 경우: 대규모 팀, 독립적 배포, 기술 스택 다양성
- AI-DLC 관점: 유닛(Unit) 개념과 매핑, 병렬 개발 가능

**6. Hybrid Architecture**
- 특징: 여러 패턴의 조합 (예: DDD + EDA, Layered + Microservices)
- 적합한 경우: 복잡한 요구사항, 다양한 컴포넌트 특성

### Phase 3: AI-DLC 10가지 원칙 기반 평가

각 아키텍처 후보를 AI-DLC의 10가지 핵심 원칙에 비추어 평가하세요:

**평가 기준:**

1. **원칙 1: 후추가가 아닌 재고**
   - 이 아키텍처가 AI 주도 개발을 자연스럽게 지원하는가?
   - 전통적 방법론의 비효율성을 강화하지 않는가?

2. **원칙 2: 대화 방향의 역전**
   - AI가 워크플로를 주도하기 용이한가?
   - 인간 승인 포인트가 명확히 정의되는가?

3. **원칙 3: 설계 기술 통합**
   - DDD, BDD, TDD 같은 설계 기술을 자연스럽게 통합할 수 있는가?
   - 품질을 유지하면서 빠른 반복이 가능한가?

4. **원칙 4: AI 능력과 정렬**
   - 현재 AI의 능력(코드 생성, 설계 제안)을 효과적으로 활용하는가?
   - 인간 감독이 자연스럽게 통합되는가?

5. **원칙 5: 복잡한 시스템 구축 지원**
   - 고급 아키텍처 복잡성을 관리할 수 있는가?
   - 확장성과 통합 요구사항을 충족하는가?

6. **원칙 6: 인간 공생 강화**
   - 인간 검증 포인트가 명확한가?
   - 품질 게이트(Quality Gate)를 설정하기 용이한가?

7. **원칙 7: 친숙함을 통한 전환 촉진**
   - 기존 팀이 쉽게 이해하고 채택할 수 있는가?
   - 학습 곡선이 가파르지 않은가?

8. **원칙 8: 책임 간소화**
   - 전문화된 역할(프론트엔드, 백엔드, DevOps) 간 장벽을 줄이는가?
   - 개발자가 전체 스택을 이해하고 작업하기 용이한가?

9. **원칙 9: 흐름 최대화**
   - 인수인계와 전환을 최소화하는가?
   - 손실 함수(Loss Function)로 품질 저하를 조기 탐지할 수 있는가?

10. **원칙 10: 하드와이어된 워크플로 없음**
    - 다양한 개발 시나리오(신규, 리팩토링, 버그 수정)에 유연하게 적용 가능한가?
    - AI가 상황에 맞는 워크플로를 제안할 수 있는가?

**평가 점수 체계:**
- 각 원칙별로 1-10점 척도로 평가
- 각 원칙의 가중치는 프로젝트 특성에 따라 조정 가능
- 총점을 기준으로 아키텍처 순위 결정

### Phase 4: 시스템 특성별 적합성 평가

사용자가 제공한 요구사항을 바탕으로, 각 아키텍처의 적합성을 평가하세요:

**평가 영역:**

1. **데이터 흐름 특성**
   - 순차적 처리 중심인가? → Pipeline 유리
   - 이벤트 기반 비동기 처리 중심인가? → EDA 유리
   - 트랜잭션 일관성이 중요한가? → Layered, DDD 유리

2. **도메인 복잡도**
   - 비즈니스 로직이 복잡하고 다양한가? → DDD 유리
   - 단순한 CRUD 중심인가? → Layered 적합
   - 데이터 변환 중심인가? → Pipeline 적합

3. **확장성 요구사항**
   - 수평 확장이 필수적인가? → Microservices, EDA 유리
   - 일부 컴포넌트만 확장이 필요한가? → DDD with Selective Scaling
   - 확장성보다 단순성이 중요한가? → Layered, Pipeline 적합

4. **팀 구조와 규모**
   - 대규모 팀, 병렬 개발이 필요한가? → Microservices, DDD 유리
   - 소규모 팀인가? → Layered, Pipeline 적합
   - 팀이 AI 도구에 익숙한가? → 모든 아키텍처 가능

5. **배포 및 운영**
   - 독립적 배포가 중요한가? → Microservices 유리
   - 모놀리식 배포로 충분한가? → Layered, Pipeline 적합
   - 무중단 배포가 필수인가? → Microservices, EDA 유리

6. **기술 부채와 레거시**
   - 기존 시스템과의 통합이 많은가? → Layered with Adapter, DDD 유리
   - 점진적 현대화가 필요한가? → Strangler Pattern with DDD
   - 완전히 새로운 시스템인가? → 모든 아키텍처 고려 가능
