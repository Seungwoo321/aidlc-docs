# Unit 5: 시스템 품질 측정 방법 구축

**우선순위**: P2 (Low Priority)
**예상 소요 시간**: 2-3일
**담당 영역**: Operations Phase

---

## 목표

콘텐츠 생성 시스템의 품질을 정량적으로 측정하는 방법을 정의하고, 시스템 효과성을 지속적으로 모니터링하는 체계를 구축합니다.

**해결하는 시스템 문제**:
- 시스템 품질 측정 방법 부재
- 생성된 콘텐츠의 품질 평가 기준 모호
- 시스템 성능 추적 및 개선 메커니즘 부재
- 반복 오류 패턴 식별 어려움

---

## 현재 상태 (As-Is)

### 문제점

1. **품질 측정 부재**
   - 파서 테스트는 있지만 정량적 품질 점수 없음
   - 생성된 콘텐츠의 품질을 어떻게 측정할지 불명확
   - "좋은" 콘텐츠와 "나쁜" 콘텐츠의 기준 모호

2. **시스템 성능 추적 부족**
   - 각 Filter의 실행 시간 측정 안 됨
   - 병목 지점 식별 어려움
   - 성능 개선 효과 측정 불가

3. **반복 오류 패턴 분석 부재**
   - 어떤 Filter에서 자주 실패하는지 추적 안 됨
   - 어떤 유형의 토픽에서 문제가 많은지 분석 안 됨
   - 개선 우선순위 결정 근거 부족

4. **개선 루프 부재**
   - 측정 → 분석 → 개선 → 재측정 루프 없음
   - 시스템이 점진적으로 개선되지 않음

### 예시: 현재 상태
```bash
# 파서 테스트만 있음 (Pass/Fail)
npx tsx test/test-overview.mjs file.md
→ Pass 또는 Fail만 알 수 있음
→ 얼마나 "좋은지" 측정 불가
→ 개선 방향 제시 없음
```

## 목표 상태 (To-Be)

### 개선 사항

**정량적 품질 측정 시스템**:

1. **품질 지표 정의**
   - 파서 테스트 통과율 (목표: 100%)
   - 콘텐츠 품질 점수 (0-100점, 목표: 90점 이상)
   - 오류 발생률 (목표: <5%)
   - Filter별 평균 생성 시간 (목표: 토픽당 <5분)

2. **손실 함수 (Loss Function)**
   - 각 품질 기준에 대한 감점 규칙
   - 총점 계산 공식
   - 개선이 필요한 영역 자동 식별

3. **성능 모니터링**
   - 각 Filter 실행 시간 측정
   - 전체 파이프라인 소요 시간
   - 병목 지점 식별
   - 시간별/토픽별 성능 추세

4. **오류 분석**
   - Filter별 실패율
   - 오류 유형별 빈도
   - 토픽별 문제 패턴
   - 반복 오류 식별

5. **개선 루프**
   - 측정 → 분석 → 개선 제안 → 재측정
   - 개선 효과 정량적 검증
   - 지속적 품질 향상

### 기대 효과

- ✅ 콘텐츠 품질 정량적 평가 가능
- ✅ 시스템 성능 병목 지점 식별
- ✅ 개선 우선순위 데이터 기반 결정
- ✅ 지속적 품질 향상 체계 구축

### 성공 기준

1. 품질 지표 정의 문서 존재
2. 손실 함수 구현 (스크립트)
3. 성능 모니터링 대시보드 (최소 로그 분석)
4. 오류 분석 리포트 자동 생성
5. 개선 효과 측정 가능

```markdown
# 시스템 품질 측정 방법

## 1. 품질 지표 정의

### 1.1 파서 테스트 통과율
- 측정 방법: 전체 파일 중 파서 테스트 통과 파일 비율
- 목표: 100%
- 수집 방법: 파서 테스트 결과 집계

### 1.2 콘텐츠 품질 점수
- 측정 방법: 손실 함수 기반 0-100점 계산
- 목표: 90점 이상
- 수집 방법: validate-*.mjs 스크립트 실행

### 1.3 오류 발생률
- 측정 방법: (실패한 Filter 실행 수 / 전체 Filter 실행 수) × 100
- 목표: <5%
- 수집 방법: 오케스트레이션 로그 분석

### 1.4 Filter별 평균 생성 시간
- 측정 방법: 각 Filter 실행 시간 측정 및 평균 계산
- 목표: 토픽당 전체 <5분
- 수집 방법: 오케스트레이션 성능 로그

### 1.5 재시도 횟수
- 측정 방법: 각 토픽당 재시도 횟수
- 목표: <1회
- 수집 방법: 오케스트레이션 로그

## 2. 손실 함수 설계

### 2.1 개요 섹션 손실 함수
```javascript
// validate-overview.mjs
function calculateOverviewScore(content) {
  let score = 100;

  // 구조적 감점
  if (!has4Subsections) score -= 20;
  if (introductionLength < 50) score -= 10;
  if (whyLearnThisReasons < 3) score -= 10;

  // 내용적 감점
  if (noConcreteExample) score -= 10;
  if (vaguePhrases > 3) score -= 5;

  return { score, errors, improvements };
}
```

### 2.2 총점 계산
```
총점 = (overview_score + concepts_score + practice_score + quiz_score) / 4
```

### 2.3 품질 등급
- 90-100: Excellent
- 80-89: Good
- 70-79: Acceptable
- <70: Needs Improvement

## 리스크 및 고려사항

### 주요 리스크

1. **과도한 측정 부담**
   - 모든 것을 측정하려다 복잡도 증가
   - 완화: 핵심 지표에 집중

2. **손실 함수 설계 어려움**
   - "좋은" 콘텐츠 기준이 주관적
   - 완화: 파서 테스트 기반, 점진적 개선

3. **성능 오버헤드**
   - 측정 자체가 시간 소비
   - 완화: 가볍게 설계, 선택적 활성화

4. **잘못된 최적화**
   - 지표만 높이려다 본질적 품질 저하
   - 완화: 다차원 지표, 정기적 수동 검토

### 고려사항

- **단순성 우선**: 복잡한 측정보다 간단한 측정 먼저
- **점진적 개선**: 기본 지표 → 고급 분석
- **인간 판단 보완**: 자동 측정 + 수동 검토
