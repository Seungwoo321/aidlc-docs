# Unit 1: Filter 계약 명시화

**우선순위**: P0 (High Priority)
**예상 소요 시간**: 2-3일
**담당 영역**: Construction Phase

---

## 목표

7개 서브에이전트의 입출력 계약을 명시적으로 문서화하여 각 에이전트(Filter)가 무엇을 입력받고 무엇을 출력하는지 명확히 정의합니다.

**해결하는 시스템 문제**:
- 에이전트 간 입출력 계약이 암묵적이어서 유지보수 어려움
- 각 에이전트의 책임과 인터페이스가 불명확
- 새로운 에이전트 추가 시 통합 방법 모호

---

## 현재 상태 (As-Is)

### 문제점

1. **암묵적 계약**
   - `.claude/agents/*.md` 파일에 I/O 명세가 명시적이지 않음
   - 에이전트가 "무엇을 받아야 하고 무엇을 만들어야 하는지" 추론해야 함
   - 예: overview-writer.md는 "개요를 작성하세요"라고만 되어 있음

2. **의존성 불명확**
   - 에이전트 A의 출력이 에이전트 B의 입력이 되는 관계가 문서화되지 않음
   - 순서 변경 시 영향 분석 어려움

3. **품질 기준 모호**
   - 각 에이전트가 만드는 산출물의 품질 기준이 명시되지 않음
   - 파서 테스트가 있지만 계약 문서에 통합되지 않음

### 예시: overview-writer의 현재 상태
```
현재: "학습 콘텐츠의 개요를 작성하세요"
→ 입력이 무엇인지 명시되지 않음
→ 출력 형식이 명시되지 않음
→ 품질 기준이 명시되지 않음
```

---

## 목표 상태 (To-Be)

### 개선 사항

각 Filter에 대해 **명시적 계약 문서** 생성:

1. **입력 계약 (Input Contract)**
   - 필수 입력 데이터
   - 입력 형식 및 위치
   - 선행 조건 (Preconditions)

2. **출력 계약 (Output Contract)**
   - 생성할 파일/섹션
   - 출력 형식 및 구조
   - 후행 조건 (Postconditions)

3. **품질 계약 (Quality Contract)**
   - 파서 테스트 참조
   - 구조적 요구사항
   - 내용적 요구사항

4. **Work Status Markers 계약**
   - 시작 시 확인할 마커
   - 완료 시 업데이트할 마커
   - 실패 시 처리 방법

### 기대 효과

- ✅ 각 에이전트의 책임 명확화
- ✅ 에이전트 개선 시 영향 범위 파악 용이
- ✅ 새로운 에이전트 추가 시 통합 방법 명확
- ✅ 디버깅 및 오류 추적 용이

### 성공 기준

1. 7개 에이전트 각각에 대한 계약 문서 존재
2. 각 계약 문서에 입력/출력/품질/마커 계약 모두 포함
3. 파서 테스트와 품질 계약 일치
4. 계약 문서 기반으로 에이전트 간 데이터 흐름 추적 가능

## 리스크 및 고려사항

### 주요 리스크

1. **현재 구현의 불완전성**
   - 기존 프롬프트가 불완전하여 그대로 문서화 불가
   - 완화: 현재 구현을 참고하되, 제대로 된 계약 정의
   - 목표: 이 문서 = 향후 구현의 사양(specification)

2. **과도한 상세화**
   - 너무 상세하면 유연성 저하
   - 완화: "무엇(What)"에 집중, "어떻게(How)"는 최소화

3. **유지보수 부담**
   - 계약 문서와 실제 구현이 불일치할 수 있음
   - 완화: Unit 3에서 프롬프트에 계약 통합, Unit 4에서 스크립트 개선

### 고려사항

- **핵심 책임**: 제대로 된 계약 문서 작성
  * 이 문서 = 향후 올바른 구현의 기준
  * 명확성, 완전성, 실행 가능성 최우선
- 현재 구현은 **참고 수준**
  * 힌트와 아이디어 제공
  * 불완전한 부분은 보완/생성
  * 맹신하지 않음
- 계약 정의 시:
  * 명확한 인터페이스 정의
  * 검증 가능한 품질 기준
  * 에이전트의 창의성을 해치지 않는 선에서 명시
