## 실행 순서 및 의존성

### Phase 1: 기반 설계 (P0 - 필수)

**병렬 불가능 - 순차 실행**

#### Unit 1 → Unit 2

**실행 순서**: Unit 1 먼저, Unit 2 다음

**의존성**:
- Unit 2는 Unit 1의 Filter I/O 계약이 필요
- Unit 1이 각 Filter의 입력/출력을 정의하면, Unit 2는 그 사이의 데이터 전달(Pipe)을 설계

**통합 계약**:
- **Unit 1 제공**: 각 Filter의 입력/출력 계약 문서
- **Unit 2 소비**: Unit 1의 I/O 계약 참조
- **Unit 2 제공**: Work Status Markers 표준 및 Pipe 메커니즘

**마일스톤**: Unit 1-2 완료 후 아키텍처 기반 확립

---

### Phase 2: 구현 개선 (P1 - 권장)

**순차 실행 권장**

#### Unit 3: Unit 1 + Unit 2 → Unit 3

**실행 조건**: Unit 1 **AND** Unit 2 완료 후 시작

**의존성**:
- Unit 1의 Filter 계약 필요 (입력/출력/품질 기준)
- Unit 2의 Pipe 메커니즘 필요 (Work Status Markers 표준)

**통합 계약**:
- **Unit 3 소비**: Unit 1의 계약, Unit 2의 마커 표준
- **Unit 3 제공**: 개선된 에이전트 프롬프트 (계약 통합됨)

#### Unit 4: Unit 3 → Unit 4

**실행 조건**: Unit 3 완료 후 시작 (Unit 1-2 간접 의존)

**의존성**:
- Unit 3의 개선된 프롬프트로 실행 필요
- Unit 1의 계약, Unit 2의 메커니즘 참조

**통합 계약**:
- **Unit 4 소비**: Unit 1-3의 모든 산출물
- **Unit 4 제공**: 개선된 오케스트레이션 스크립트

**마일스톤**: Unit 3-4 완료 후 Construction Phase 종료

---

### Phase 3: 운영 및 측정 (P2 - 선택)

#### Unit 5: Unit 1-4 → Unit 5

**실행 조건**: Unit 1-4 완료 후 시작

**의존성**:
- Unit 1의 품질 기준 필요
- Unit 2의 상태 추적 메커니즘 필요
- Unit 3의 개선된 프롬프트로 생성된 콘텐츠 측정
- Unit 4의 성능 로깅 통합 필요

**통합 계약**:
- **Unit 5 소비**: Unit 1-4의 모든 산출물
- **Unit 5 제공**: 품질 측정 시스템, 손실 함수, 성능 모니터링

**추가 단계**:
1. 개선된 시스템으로 10-20개 콘텐츠 생성
2. 품질 데이터 수집 및 분석
3. 개선 제안 리포트 생성

**마일스톤**: Unit 5 완료 후 Operations Phase 종료

## 유닛 간 통합 계약

### 1. Unit 1 ↔ Unit 2

| 항목 | 내용 |
|------|------|
| **인터페이스** | Unit 1의 Filter I/O 계약 문서 |
| **데이터 형식** | 마크다운 문서 (각 Filter별 계약) |
| **통합 지점** | Unit 2가 Unit 1의 I/O 정의를 읽고 Pipe 설계 |
| **검증 방법** | Unit 2의 Pipe 메커니즘이 Unit 1의 모든 Filter I/O를 처리 가능한지 확인 |

### 2. Unit 1, Unit 2 ↔ Unit 3

| 항목 | 내용 |
|------|------|
| **인터페이스** | Unit 1의 계약 + Unit 2의 마커 표준 |
| **데이터 형식** | 마크다운 문서 |
| **통합 지점** | Unit 3가 프롬프트에 계약과 마커 처리 통합 |
| **검증 방법** | 개선된 프롬프트가 계약 및 마커 표준과 일치하는지 파서 테스트 |

### 3. Unit 1, Unit 2, Unit 3 ↔ Unit 4

| 항목 | 내용 |
|------|------|
| **인터페이스** | Unit 1-3의 모든 산출물 |
| **데이터 형식** | Bash 스크립트, 마크다운 문서 |
| **통합 지점** | Unit 4가 오케스트레이션에 계약, 마커, 프롬프트 통합 (설계 + 구현) |
| **검증 방법** | 개선된 v6 스크립트로 전체 파이프라인 실행 성공, 파일럿 콘텐츠 생성 및 파서 테스트 통과 |
| **구현 방식** | 기존 v6 스크립트 개선 (v7 신규 작성 보류) |

### 4. Unit 1, Unit 2, Unit 3, Unit 4 ↔ Unit 5

| 항목 | 내용 |
|------|------|
| **인터페이스** | Unit 1-4의 모든 산출물 + 생성된 콘텐츠 |
| **데이터 형식** | 스크립트, 로그 파일, 생성된 마크다운 |
| **통합 지점** | Unit 5가 품질 측정 시스템을 Unit 4 스크립트에 통합 |
| **검증 방법** | 품질 점수, 성능 데이터, 오류 분석 리포트 생성 성공 |

## 전체 타임라인

### 시나리오 1: 전체 개선 (Full Implementation)

```
Week 1:
  Day 1-2: Unit 1 (Filter 계약 명시화)
  Day 3-4: Unit 2 (Pipe 메커니즘 명시화)
  Day 5: 통합 검증 (Unit 1-2)

Week 2:
  Day 1-3: Unit 3 (에이전트 프롬프트 개선)
  Day 4-5: Unit 4 (오케스트레이션 개선)

Week 3:
  Day 1-2: Unit 5 (품질 측정 방법 구축)
  Day 3-5: 데이터 수집 및 분석 (10-20개 콘텐츠 생성)

총 소요 시간: 3주
```

### 시나리오 2: 빠른 시작 (Quick Win)

```
Week 1:
  Day 1-2: Unit 1 (Filter 계약 명시화)
  Day 3-4: Unit 2 (Pipe 메커니즘 명시화)
  Day 5: 통합 검증

→ P0 완료, 아키텍처 기반 확립
→ Unit 3-5는 향후 진행

총 소요 시간: 1주
```

### 시나리오 3: 단계적 개선 (Incremental)

```
Sprint 1 (1주): Unit 1-2 (P0)
Sprint 2 (1주): Unit 3 (P1)
Sprint 3 (1주): Unit 4 (P1)
Sprint 4 (1주): Unit 5 (P2)

총 소요 시간: 4주 (각 Sprint 사이 검증 및 조정 시간 포함)
```

## 통합 리스크 및 완화 전략

### 리스크 1: 유닛 간 인터페이스 불일치
**증상**: Unit A의 출력이 Unit B의 기대와 다름
**완화**:
- 각 유닛 완료 시 통합 계약 검증
- 문서 형식 표준화
- 예시 및 템플릿 제공

### 리스크 2: 순차 의존성으로 인한 지연
**증상**: Unit 1 지연 시 전체 일정 지연
**완화**:
- P0 유닛(Unit 1-2)에 충분한 시간 배정
- 일일 진행 상황 체크
- 필요시 범위 조정

### 리스크 3: 통합 테스트 부족
**증상**: 각 유닛은 완료되었지만 통합 시 문제 발생
**완화**:
- 각 마일스톤마다 통합 검증
- 전체 파이프라인 end-to-end 테스트
- 파일럿 콘텐츠 생성으로 검증

### 리스크 4: 범위 확대 (Scope Creep)
**증상**: 개선 과정에서 추가 기능 요구
**완화**:
- 각 유닛의 In Scope / Out of Scope 명확히 정의
- 추가 기능은 다음 반복에서 처리
- 핵심 기능 우선 완료
