# Unit 2: Pipe 메커니즘 명시화

**우선순위**: P0 (High Priority)
**예상 소요 시간**: 2-3일
**담당 영역**: Construction Phase

---

## 목표

Work Status Markers 기반 Pipe 메커니즘을 명시적으로 설계하고 문서화하여 Filter 간 데이터 전달 방식을 표준화합니다.

**해결하는 시스템 문제**:
- Pipe 메커니즘(Work Status Markers)이 명시적이지 않음
- Filter 간 데이터 전달 방식이 일관되지 않음
- 작업 상태 추적 및 재시작 메커니즘 불명확

---

## 현재 상태 (As-Is)

### 문제점

1. **Work Status Markers의 비명시성**
   - 현재 마크다운 파일 내 주석으로 작업 상태 표시
   - 마커 형식이 문서화되지 않음
   - 예: `<!-- Work Request: overview-writer -->`의 의미와 사용법 불명확

2. **데이터 전달 방식 불명확**
   - Filter가 어떻게 이전 Filter의 출력을 읽는지 암묵적
   - 마크다운 파일이 Pipe 역할을 하지만 명시되지 않음
   - 부분 완료 파일 처리 방법 모호

3. **상태 관리 메커니즘 부재**
   - 어떤 Filter가 완료되었는지 추적 방법 불명확
   - 실패 시 재시작 지점 결정 어려움
   - 병렬 처리 불가능 (순차 처리만 가능)

### 예시: 현재 Work Status Markers
```markdown
<!-- Work Request: overview-writer -->
<!-- Status: pending -->

...콘텐츠...

<!-- Status: completed -->
<!-- Work Request: concepts-writer -->
```
→ 마커의 정확한 의미, 사용 규칙, 처리 방법이 문서화되지 않음

   - 마커 위치 규칙 정의

2. **데이터 전달 프로토콜**
   - Filter 간 데이터 전달 방식 명시
   - 마크다운 파일 구조 표준화
   - 섹션별 소유권 정의

3. **상태 관리 메커니즘**
   - 작업 진행 상태 추적 방법

   - 실패 처리 프로토콜

4. **확장 가능성 설계**
   - 새로운 Filter 추가 시 통합 방법
   - 병렬 처리 가능성 고려
   - 조건부 Filter 실행 지원

### 기대 효과

- ✅ Filter 간 데이터 전달 방식 표준화
- ✅ 작업 상태 추적 및 재시작 용이
- ✅ 오케스트레이션 스크립트 개선 기반 제공
- ✅ 시스템 확장성 향상

### 성공 기준

2. Pipe 메커니즘이 명확히 문서화됨
3. 7개 Filter에 적용 가능한 일관된 프로토콜
4. 재시작 및 실패 처리 알고리즘 정의

## 리스크 및 고려사항

### 주요 리스크

1. **파일 기반의 한계**
   - 동시성 제어 어려움
   - 완화: 현재는 순차 처리만 지원, 향후 확장 고려

2. **마커 파싱 오류**
   - 마커 형식 오류 시 전체 시스템 영향
   - 완화: 명확한 형식 정의, 검증 로직 포함

3. **과도한 복잡성**
   - 너무 복잡하면 유지보수 어려움
   - 완화: 최소한의 필수 기능만 포함, 단계적 확장

### 고려사항

- **단순성 우선**: 현재 시스템의 단순함 유지
- **점진적 개선**: 기본 메커니즘 먼저, 고급 기능은 향후
- **하위 호환성**: 기존 생성된 콘텐츠와 호환 유지
